Case Study 2: Shipping safely and keeping the game smooth

In short: testing for performance and release work: a costly recolour, a chat safety fix, and nothing published untested.

What I do on this project

ChocoNeko is a Roblox game with four places: Hub, TD Survival, Incrediblox and Cooking. It's published but not publicly launched yet. I've led it for about six months, since April 2026. AI agents write and fix the code, and a reviewer bot reviews every pull request. I set direction, playtest, and approve each reviewed pull request. I work alongside an artist, a writer and a world builder, who give the game its look, story and world.

1. Day/night colour changes: about 12 ms down to about 2 ms, in two steps

The problem: The HUD and chat gradually change colour from day to night. That recolour was expensive and could make the chat flicker. The flicker was flagged to me after an earlier fix, and I then saw it myself in playtests.

How it was measured: In-game timing counters, read during Studio playtests on my PC, including one run of about 8 minutes. These are Studio numbers from one PC, not the published game or a phone.

Step 1: Chat repaint cost used to grow with message history. The first fix made it independent of history and recoloured rows in place. The chat's cost per frame went from about 12 ms, with spikes up to about 30 ms, to about 5 ms.

Step 2: The chat recolour was then spread across several frames instead of one. Most frames came down to about 2 ms, and the visible flicker was gone.

My part: I tested each step with a mix of Studio and published-game playtests.

2. A chat filter fix before public launch (Oct 2)

What happened: We found and fixed a case where chat styling data could bring back words the filter had hidden, before public launch.

My part: I tested the fix myself, both in Studio and on the published game, to be sure.

Why it matters: On Roblox, chat filtering protects players, many of whom are kids. Anything that shows filtered words to another player is a safety problem, not a cosmetic bug.

3. A publish script that only touches what changed

Why it started: I used to publish each place by hand in Studio. Once shared systems spanned all four places, doing that by hand got tedious and easy to get wrong, so I proposed a publish pipeline. The agents built it with Lune and Roblox Open Cloud, and it's designed to be careful:

  • Nothing uploads unless the command explicitly says to publish, confirms it, and includes a note.
  • A plan step lists which places would change before anything happens.
  • It downloads each published place first and puts the new code on top, so anything built in Studio is kept.
  • If a place is open in Studio, the upload stops with a "server busy" error instead of overwriting it.

A "changed" mode picks only the places affected by changed files. Shared code, like the HUD, still means all four places.

Why that matters to me as a tester: Every published place could break, so re-uploading untouched places adds risk for nothing. It also shows what to retest.

4. Nothing is published until I've tested it

How a change gets out:

  1. An agent opens a pull request, the reviewer bot reviews it, and I approve it.
  2. It's merged to main, and main is pulled onto my PC.
  3. Rojo live-syncs the code into Studio (one Rojo server per place), and I test the change there.
  4. Nothing publishes until I say "publish".

After publishing: I always recheck on the published place. It's the real build, and the MicroProfiler is less noisy there than in Studio. For example, I tested a hover fix in Incrediblox in Studio, then rechecked it on the published place. The average frame time went from about 9.1 ms to about 6.6 ms in the MicroProfiler.

Checking before fixing: I retested an Alt keybind report on the published game and confirmed it was already working, so nothing needed fixing. Checking first avoids changing code that isn't broken.

Why I keep that gate: A reviewed pull request means the code reads well, not that the game plays well.

What I learned

  • Performance is testable. Timing counters turn "it seems heavy" into before/after numbers.
  • Know where your numbers come from. Studio on one PC isn't a phone or the published game, so I say which is which.
  • Severity isn't about visibility. A chat filter problem outranks a cosmetic glitch because it affects player safety.
  • Smaller releases are easier to test. Publishing only what changed shows what to retest.
